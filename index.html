Instant disposable Windows environments.

Run the Windows commands, builds, tests, desktop apps and vendor .exe tools your Mac can't run natively — in clean, disposable local Windows. Each run starts from the same clean state and throws its writable disk away. No long-lived Windows VM to patch, snapshot or babysit.

What you can do

Run, build, test and automate Windows — from a Mac.

Run Windows software

Windows commands, .exe tools, vendor and legacy closed-source utilities, PowerShell — with stdout, stderr and the exit code returned unchanged. Sysinternals and x64 binaries run under emulation.

winquick run -- pwsh -File .\build.ps1

Build and test projects

Copy a workspace into Windows, build or test, and pull back only the artifacts you name. Modern .NET and .NET Framework down to legacy targets, with packages restored offline first.

winquick build ./MyApp -c Release

Bring your own tools

Register a Windows toolchain once as a cached volume; every disposable run then has it on PATH, with no re-copy of the toolchain. Verified with Go, Node, Python, Zig and a C compiler.

winquick tool add go --from ./go

Automate desktop apps

Launch a GUI app that runs on Validation OS in a headless session, capture screenshots, and drive the controls it exposes through Microsoft UI Automation. WPF and WinForms are verified end to end.

winquick ui-test MyApp.csproj --script smoke.uitest

Give agents a Windows runtime

A native MCP server exposes the run, desktop and UI-automation tools over stdio, so Claude, Cursor or any script can drive real Windows — without keeping a Windows box around.

claude mcp add winquick -- winquick mcp

Disposable and offline

Changes made during a run are discarded; the base image and caches are kept. The guest starts with no network device, and only the artifacts you request are copied out. It is not a hardened malware sandbox.

winquick run -w . -a "bin/**" -- dotnet publish -c Release

Why not just a VM

For running Windows software from a Mac, a VM is a lot to keep alive.

A Windows VM

  • Boot it, then keep it running between tasks
  • Patch Windows, manage disk and snapshots
  • Copy files in and out by hand
  • State from the last run is still there
  • Gigabytes resident whether you are using it or not

WinQuick

  • One command; nothing runs between tasks
  • Nothing to patch — the run's disk is thrown away
  • Workspace copied in, only requested artifacts out
  • Every run starts from the same clean Windows
  • Local, scriptable, and warm in about 310 ms

This is about one workflow — running, building and testing Windows software from a Mac. WinQuick is not a general-purpose VM manager and does not replace one for interactive Windows use.

Each run

How a run works.

  1. 1
    Workspace copied inA copy, so changes inside Windows are not copied back.
  2. 2
    Windows runs cleanThe guest starts with no QEMU network device.
  3. 3
    Requested artifacts copied outThe run's writable disk is then discarded.

Fast enough to put in a script

A real Windows command in about a third of a second.

The first winquick setup downloads and prepares the Windows runtime once. Every run after that resumes a prepared Windows in ~310 ms — no long-lived VM to keep patched and running between tasks.

~310 msclean Windows, cmd /c ver
~520 msdotnet --version
~690 msPowerShell 7 start-up
~340 msdesktop session start
~2.9 sgo build → a Windows .exe
~0.7 sprettier formats real JS

Measured on Apple Silicon M4 Pro, macOS 26, warm prepared guest. go build and prettier ran offline through tool volumes. 100 runs of cmd /c ver gave p99 319 ms, zero failures. The first setup is a one-time download and prepare, not part of these figures. Apple Silicon is the supported host; Windows and Linux are a future plan.

Desktop applications

Run and test Windows desktop applications.

The desktop capability starts a headless Windows desktop. GUI apps that run on Validation OS can be launched and screenshotted; apps that expose Microsoft UI Automation can also be inspected and driven by control rather than by pixel. WPF and WinForms are verified end to end — built inside Windows, then driven — while an app with no useful automation surface can still be captured, just not clicked.

Install

Install on macOS.

  • An Apple Silicon Mac (M1 or newer), macOS 13 (Ventura) or later
  • QEMU 11 or newer — Homebrew installs it for you
  • About 8 GiB of free disk for the Windows runtime and tools
  • Microsoft's Validation OS image (~2.4 GB), downloaded once by winquick setup under Microsoft's licence
  • Not inside a nested virtual machine — WinQuick needs real hardware virtualisation
Supported host

macOS · Apple Silicon

Homebrew is the supported install path — it pulls in QEMU and hivex and is not quarantined by Gatekeeper. A direct archive download works too, but is unsigned until notarized.

brew install carlbomsdata/tap/winquick
Future plan

Windows & Linux

WinQuick runs only on macOS with Apple Silicon today. WHPX and KVM host code paths exist in the repository, but neither is supported or released yet. Watch the repository for progress.

Honest limits

What it does not do — so you can trust what it does.

  • macOS Apple Silicon only — Windows and Linux host paths exist in the tree but are a future plan, not supported.
  • The guest is minimal — Microsoft Validation OS. A tool that needs a Windows service it lacks will not run.
  • Not every GUI is drivable — apps launch and screenshot, but only those exposing UI Automation can be clicked.
  • Homebrew is the path today — a direct archive download is unsigned until Developer ID notarization exists.
  • Not a malware sandbox — it is a hardware-VM boundary for your own builds and tools, not an audited containment system.
  • No account, no telemetry, no daemon — it runs locally and sends nothing anywhere.
